## 2. P0 — 崩溃 / 丢数据（立即处理）

### 2.1 `Math.max(...valid)` 展开超栈
`calculator.ts:174` 用 `Math.max(...valid)` 展开整个数组求最大值。V8/WebKit 实参上限约 **65,536**，Wahoo 5Hz 记录骑行 5 小时即 ~9 万点 → `RangeError: Maximum call stack size exceeded`，且抛在 Worker 内会被 `parseClient` 判为整批失败。**收益**：消除超长活动导入崩溃。**修复**：`maxOf` 改 for 循环；同时 `records.map()×4` 可合并为单次遍历。

### 2.2 赛段页 N+1 + 全量克隆
`SegmentsPage.tsx:116-123` 对 `summaries` 逐个 `await getRecords(id)`（N+1，仓库已有批量 `getRecordsByActivityIds` 却未用），随后把**全部活动的全量 records**（200 活动×8000 点≈160 万对象）塞进每个赛段的 `postMessage`，结构化克隆 × 赛段数 → 数十秒卡死、峰值内存翻倍。**收益**：秒级 + 内存可控。**修复**：一次批量取 records，inputs 只传一次，赛段在 Worker 内循环。

### 2.3 无 ErrorBoundary + PWA 更新白屏
全仓 0 个 ErrorBoundary（grep 确认）。配合 `vite.config.ts:27` `autoUpdate` + `main.tsx:15` `registerSW({immediate:true})` 但**未注册 `onNeedRefresh`**（第 26 行注释声称实现却无代码）：发版后旧标签持有的 chunk hash 失效，`lazy()` 动态 import 404 → 叠加无 ErrorBoundary → 整站白屏。**收益**：发版平滑、单页错误可降级。**修复**：加一个 `ErrorBoundary` 包 `Routes`；补 `onNeedRefresh` 提示刷新。

### 2.4 解析 Worker 不回收、无超时
全仓仅 `leaderboardClient.ts:77` 有 `terminate()`；`parseClient.ts` 从不 terminate 且无超时。Worker 崩溃/OOM 后 `postMessage` 静默无响应 + 无超时 → `importFiles` 的 `await` 永久悬挂，进度条卡死且 `importing` 恒 true（UI 不可关闭），每批还泄漏一个含 fitsdk 的 Worker。**收益**：导入失败可恢复。**修复**：`parseClient` 加超时 + 失败 `terminate` + 任务级 cleanup。

### 2.5 Dexie 无迁移 / 无升级监听
`db.ts` v1→v4 全程无 `.upgrade()`，且无 `db.on('versionchange'/'blocked')`。当前因「只增表」侥幸不丢数据，但**未来任何迁移都会丢数据**；且多标签页打开时旧标签持连接，升级被 block，新标签卡在 `db.open()`。**收益**：多标签页死锁解除、迁移可落地。**修复**：补 `on('blocked')` 提示 + 为未来版本预留 `.upgrade()`。

## 3. P1 — 正确性 / 明显性能

### 3.1 爬升算法 + 已解码字段零引用
`calculateElevationGain`（`calculator.ts:125-137`）裸累加相邻正增量，气压高度量化噪声（±0.5~1m@1Hz，3 小时≈1 万点）可凭空产生数百米爬升。而 `fitDecoder.ts:283` 已解码的 `session.totalAscent/totalDescent` **全项目零引用**（grep 确认）。`climbs.ts` 已有 30m 尖刺过滤 + 80m 窗口平滑，但摘要「爬升」与「爬坡段累计」两套口径永不对齐。**建议**：摘要优先采用 `session.totalAscent`，或加累计阈值平滑。

### 3.2 时区口径分裂 ⚠️（高度可疑的真 bug）
`activityRepository.ts:261` 月份筛选用 `startTime.startsWith(month)` 走 **UTC 前缀**；而 `calendarData.ts` / `statistics.ts` / `weeklyStats.ts` 用 `localDateKey` 走**本地时区**。东八区 23:00 的活动会归类错乱。**强信号**：全量测试恰有 **2 个失败用例**，且都涉日期——`DashboardPage`「本周/本月/总计（跨月数据）」与 `statisticsPage`「自定义范围按起止日期过滤（含边界日）」——**今天正是 2026-09-01 跨月日**。建议优先排查此项是否为根因（失败用例非测试脆弱，是真实逻辑与时区相关的边界问题）。

### 3.3 训练指标算法口径
- `avgCadence` 计入滑行 0 值（行业口径排除 0）→ 系统性偏低；`estimateDistance` 同理 `speed ?? 0` 低估。
- `normalizedPower.ts` 先过滤无功率点再开窗，且从第 0 点就 push 未满 30s 的窗口均值（标准需窗口填满）。
- `powerCurve.ts:88` 双指针窗口偏大（停在 `span>=duration` 首点而非最近点）→ 各时长最佳功率系统性偏低。
**收益**：指标更接近 Strava，用户对比基线可信。**注意**：改动会改变既有数值，需同步更新快照类测试。

### 3.4 坐标 `?? 0` 落库
`ActivityDetailPage.tsx:522-525` 建赛段时 `first.latitude ?? 0` 把缺失坐标以 0 落库 → 写入 (0,0) 几内亚湾。**修复**：前置校验，坐标缺失时拦截而非写 0。

### 3.5 `buildClimbs` 详情页重复计算
`buildClimbs` 是 O(n·w)（每点扩展 80m 窗口，w≈32）。它在一次详情页渲染中被 `computeQualityScore`(内调)、`SegmentsSection`、`rideInsights` 共 **3 次**调用（grep 确认 3 个调用点）。**修复**：详情页 `useMemo` 算一次，下传给各 section。

### 3.6 首屏体积
`index.html` 实测 `modulepreload` 了 `recharts`(412kB/119kB gzip) 与 `dataSourceStore`(103kB/35kB gzip)：
- `App.tsx:6` 静态引入 `DashboardPage`（首屏即含 Recharts）；
- `AppLayout` 静态引 `ImportPanel → importStore → importer → Dexie + fflate`。
**收益**：首屏 JS 由 ~1.5MB 降到主要 `index`(266kB)；懒加载仪表盘图表、把 importer 改动态 import。**注意**：`App.tsx:7-9` 注释声称"Recharts 按需进入各页面 chunk"与实际不符。
