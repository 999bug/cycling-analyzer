# 小程序原生重构方案（数据打进包 · 零域名上线）

> 目标：用**原生微信小程序**承载「骑行分析」，支持微信内打开、分享获客、导入自己的 FIT、完整分析；
> 优先做到**零域名（不买域名、不备案）也能开发、调试、上线**；复用现有 web 项目的框架无关核心。
> 本文为方案文档，待确认后启动实施。

---

## 0. 结论速览

1. **放弃 web-view 方案**：web-view 需要「业务域名」且必须 ICP 备案，`999bug.github.io` 是 GitHub 域名无法备案，真机/发布走不通。
2. **走原生小程序 + 数据打进包**：可行，且能零域名上线。
3. **体积实测（public/author-data）**：
   - 逐点 `records` 层：**125 MB**（单文件最大 7 MB）→ **不能整包打进**（小程序包上限：主包 ≤ 2MB、含分包总计 ≤ 20MB）。
   - 摘要/预聚合/index 层：**347 KB**（`activities.json`、`manifest.json`、`profile.json`、`precomputed/*`）→ **可打进主包，离线即用**。
4. **零域名能覆盖的功能**：仪表盘、活动列表、统计卡片、地图（预计算 tracks）、功率曲线、路线组、个人档案——全部来自 347 KB 层。
5. **125 MB 逐点数据**用两种方式处理：① 抽稀后进**分包**（≤2MB/包）做作者活动完整流图；② 或作者数据仅到预聚合层，**完整逐点分析留给用户自己导入的 FIT（本地全功能）**。

## 1. 目标与硬约束

### 目标
- 微信内打开、分享到朋友圈/群（获客）；
- 用户导入自己的 FIT 文件并做完整分析；
- 浏览作者公开数据；
- 最终**零域名上线**。

### 微信硬约束（必须时刻牢记）
| 约束 | 数值/规则 | 对本项目影响 |
|---|---|---|
| 主包大小 | ≤ 2 MB | 摘要层 347K 安全 |
| 单个分包大小 | ≤ 2 MB | 抽稀后 records 需压到 2MB 内 |
| 总包大小（主+分包） | ≤ 20 MB | 全量 records 125M 绝对超 |
| 网络域名 | 需 ICP 备案 + 后台配置 | **零域名 = 不调用 wx.request 到外部、不用 web-view** |
| 个人主体 | 无微信支付 | 变现靠后续企业主体；本期不影响 |

## 2. 数据体积与打包策略

```
public/author-data/
├── activities.json          摘要列表        ← 打进主包（离线）
├── manifest.json            清单            ← 打进主包
├── profile.json             训练档案        ← 打进主包
├── precomputed/
│   ├── power-records.json   功率曲线(预计算) ← 打进主包
│   ├── route-groups.json    路线分组(预计算) ← 打进主包
│   └── tracks.json          简化轨迹(预计算) ← 打进主包（地图用）
└── records/                 ★ 逐点流数据 125MB ← 不能直接打进包
    └── <hash>.json          单活动全量流（速度/心率/海拔/经纬度…）
```

### 策略 A：作者数据离线（零域名）
- **主包**：放 347 KB 摘要/预聚合层 → 仪表盘、列表、统计、地图、功率曲线全部离线可用。
- **分包 `author-detail`**：把 `records` **抽稀**（例如按时间/距离重采样到 ~300–500 点）后打入，≤ 2MB，供作者活动「完整流图」离线展示。
  - 若抽稀后仍超 2MB，则作者活动详情降级为「预聚合 + 关键指标」，完整逐点流图仅对用户自有数据开放。

### 策略 B：用户自有数据（零域名，全功能）
- 用户通过 `wx.chooseMessageFile` 从「文件传输助手」选 `.fit` → 本地读取 → **Worker 内解析**（见 §6）→ 归一化 → 存入本地（storage + 文件系统）。
- 用户数据**完整逐点**，离线全功能，不联网、不需要域名。

## 5. 数据打进包的具体机制

### 5.1 核心同步脚本 `scripts/sync-core.mjs`
- 把 `src/fit/normalizer`、`src/fit/calculator`、`src/features/analysis`、`src/features/statistics`、`src/utils`、`src/types` 复制到 `miniprogram/core/`。
- 过滤掉任何 `window`/`document`/`indexedDB` 引用（构建期报错即停）。
- 单向同步：`src/` 为唯一真相源，避免双份维护。

### 5.2 数据同步脚本 `scripts/sync-author-data.mjs`
- 复制 `public/author-data` 的 347 KB 层 → `miniprogram/data/author/`。
- **JSON → JS 模块**：`xxx.json` 转为 `module.exports = {...}` 的 `xxx.js`，用 `require('../../data/author/xxx.js')` 读取（避开小程序包内文件路径读取的限制，且可懒加载）。
- 生成 `index.js` 清单（活动 id → 模块路径），供懒加载。

### 5.3 抽稀脚本 `scripts/decimate-records.mjs`
- 读取 `public/author-data/records/*.json`，按时间/距离重采样到目标点数（如 400 点）。
- 输出到 `miniprogram/subpackages/author-detail/records/`，确保单分包 ≤ 2MB。
- 若超限：降低目标点数或仅保留核心流（距离/海拔/心率），直到达标。

### 5.4 读取方式
- 作者源：`require` 静态模块，**只读**；
- 我的源：本地 `getStorage` / `getFileSystemManager` 读取，可写。

## 6. 头号风险（已排除）：FIT 解析在 MP 逻辑层

**实测结论**：`@garmin/fitsdk` v21 是**纯 JavaScript 实现（无 .wasm 文件）**，仅依赖标准 `DataView`/`TypedArray` + `TextDecoder`。原方案担心的「WASM 在 Worker」风险**不成立**——风险大幅降低。

- **已验证**：通过 `scripts/sync-fitsdk.mjs` 把 ESM 源转成 CommonJS 复制到 `miniprogram/vendor/fitsdk/`，在 Node 端用真实 `.fit`（`tests/fixtures/power-only.fit` 等）端到端解码成功（`isFIT`/`checkIntegrity` 为 true，record/session 解析正常，功率/坐标换算正确）。
- **MP 适配点**：
  1. 小程序逻辑层**全局无 `TextDecoder`**，已在 `miniprogram/fit/textDecoderPolyfill.js` 注入最小 UTF-8 解码器（仅在缺失时生效，Node/浏览器环境跳过）；
  2. 当前**先在逻辑层（主线程）解码**（`miniprogram/fit/normalize.js`），导入页直接调用；若后续大文件（7MB）卡顿，再拆到 `workers/fitParser.js`（方案预留，非必须）。
- **为什么不用 Worker**：降低联调复杂度与不可验证风险；主线程解码数百 KB–数 MB 文件在实际机型可接受。

> 备选仍保留：若主线程解码体验差，再上 Worker（纯 JS 在 Worker 同样可跑，无需 WASM 兜底）。

## 8. FIT 导入流程（本地、零域名）

```
用户点「导入」→ wx.chooseMessageFile（从文件传输助手选 .fit）
  → FileSystemManager.readFile 得 ArrayBuffer
  → 逻辑层直接解码(miniprogram/fit/normalize.js：fitsdk 转 CJS + TextDecoder polyfill)
  → normalizer 归一化(复用 calculators 算法) → 摘要+ID 去重
  → 存本地(myRepository：摘要进 storage，逐点流图按 ID 存 storage)
  → 切换数据源为「我的」→ 更新活动列表
```
> 当前在逻辑层（主线程）解码，未用 Worker（纯 JS 在 Worker 亦可，待大文件卡顿再拆）。
- 与 web 端 `importer`/`stravaExport` 逻辑对齐（标题还原、去重指纹），但改为 MP API。
- 导入失败进台账可重试（沿用 web 的 fileRepository 思路）。

## 12. 用户答疑（数据可见性 / 上传 / 周期）

> 本节锁定产品决策，启动实施前已与用户确认。

### Q1. 开发周期？
- **最快见效果 / 获客起点**（Phase 0–1，离线读作者数据 + 仪表盘）：约 **2–3 周**（已交付 ✅）。
- **能导入自己 FIT**（Phase 0–3，主线程解码 + 本地存储 + 双数据源）：Phase 0–3 已完成 ✅，已可在 DevTools 验收导入。
- **完整功能上线**（Phase 0–6，图表+地图+分享+优化+提审）：剩余 Phase 4(地图)/5(分享)/6(优化提审) 待推进。
- **风险更新**：fitsdk 是纯 JS（非 WASM），已在 Node 验证可解码，Phase 3 不确定项已消除（详见 §6）。
- 用户侧前期仅需：注册小程序拿 AppID、偶尔点一次 GitHub Pages 部署；其余由开发方完成。

### Q2. 用户可以上传自己的 FIT 文件吗？
- **可以，全程不联网。**
- 机制（§8）：把 `.fit` 转发到微信「文件传输助手」→ 小程序内点「导入」→ `wx.chooseMessageFile` 选取 → 本地读二进制 → Worker 解析 → 归一化 → 存手机本地。
- 本地为**完整逐点数据**，完整分析（速度/心率/海拔/功率曲线）均可用，比作者打包的抽稀数据更全。
- 小程序不能像电脑直接打开系统文件夹，故走「微信会话选文件」官方通道（单文件上限充足，7MB 无压力）。

### Q3. 别人（其他用户）也能上传自己的 FIT 吗？
- **能。** 每个用户手机上是独立小程序实例，导入机制一致：各自本地选、本地解析、本地存，不依赖服务器。

### Q4. 用户能看到别人的数据吗？
- **默认看不到**（零域名离线设计的核心特征）：
  - ✅ 作者公开数据（打包进主包）：人人可见 → 即「看作者骑得怎样」；
  - ✅ 用户自己数据：仅本人手机可见；
  - ❌ 用户之间数据：**互不可见**（无后端同步）。
- 优点：隐私天然好、无需服务器/域名。
- 局限：做不了社区/排行榜/看好友骑行。
- **若日后要「看别人数据 / 社区」**：必须上云后端（买域名+备案+服务器，数据上传到服务端），进入付费后续阶段，会打破零域名方案。
- **折中获客**（不破坏零域名）：用 `onShareAppMessage` 分享「某次骑行成绩卡/图表截图」给好友——好友看到生成的成绩图/卡片，而非原始数据，足以做朋友圈裂变。

### 数据可见性决策小结
| 数据 | 可见范围 | 是否需服务器 |
|---|---|---|
| 作者公开快照（打包） | 所有用户 | 否（打进包） |
| 用户自有 FIT | 仅本人 | 否（本地） |
| 用户间数据 | 不可见 | — |
| 社区/排行榜/好友数据 | 需上云后端 | 是（域名+备案+服务器） |
