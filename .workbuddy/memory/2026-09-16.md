### P1-1（v8 localDate 索引 + 查询规划器）——三处认知纠正，改动前先看

- **`activities.startTime` 是 UTC ISO 字符串，不是 Unix 秒**（`normalizer.ts:110` 用 `toISOString()` 产出，
  格式统一 → 字典序等价于时间序，所以能直接当排序索引用）。我方案初稿写成「Unix 秒」是错的，已更正。
  真正需要新开 `localDate` 的原因：年/月筛选按**本地时区**日期前缀匹配，与 UTC 日期在边界不等价
  （UTC 8-31 23:30 在东八区是 9-1）。
- **`[activityType+startTime]` 复合索引被砍掉**（初稿列了）：库里 `activityType` 存的是平台原始写法
  （`road_biking`/`骑行`），筛选传的是归一化值（`cycling`），复合索引只命中字面量相等的行 →
  **静默漏记录**，比不走索引更糟。类型筛选继续走内存精筛。
- **oracle 必须补「同值按 id 排序」兜底**：IndexedDB 索引倒序扫描时同键按**主键倒序**返回，
  而内存排序保留插入序（主键升序）。`startTime` 精度到秒，同值并非不可能。不补这层，
  索引路径与 oracle 在存在同值行时页序不同，一致性测试会随机飘。
- **oracle 与索引必须同源**：`queryActivityList` 的年/月与日期区间筛选改为优先读摘要已存的 `localDate`，
  缺失才按 `startTime` 现算。否则用户跨时区后，「索引按存储值筛、内存按当前时区重算」会给出两种结果。
  **作者快照刻意不写 localDate**（会在 CI 机器时区下算出来，污染访问者口径）。
- 回填（`src/storage/localDateBackfill.ts`）：主键游标单次全表扫描 + 分批事务，**不要用
  `filter(缺字段).limit(n)` 循环**——`startTime` 非法的行永远补不上，会死循环。落 `localDateIndexReady`
  标志，未就绪时年/月筛选自动回退全量，不做「索引一定在」的隐式假设。

## P1 基线实测完成（提交 `47b4b17`，不改版本号）

新增 `scripts/bench-data-layer.ts`（`npm run bench:data-layer`，`--scale=small|default|large`）。

### 测量方法（下次测性能直接复用）

- **主口径 = IndexedDB 实际解出的行数/点数**，用 Dexie 的 `db.<table>.hook('reading', ...)` 计数
  （对象已解出、即将交给调用方时触发）。**不要用墙钟耗时**——脚本跑在 fake-indexeddb（纯内存）上，
  与真实浏览器（磁盘+结构化克隆+IPC）无可比性；而「解出行数」同时决定反序列化开销与峰值内存，
  且跨环境完全一致，可断言、可守护。
- 字节数由 `JSON.stringify(records).length` 估算（合成数据同构），**高估真实 IDB 占用**
  （IDB 用结构化克隆，不重复字段名），只能横向比较。

### 数字（scale=default）

| 场景 | 结果 |
| --- | --- |
| 列表 `toArray()` 全量（对照） | 解 1000 行 |
| `listActivities({limit:50})` 首页 | 解 50 行（20x 改善，P1-1 已达标） |
| 同上 `offset=950` 尾页 | 仍只解 50 行，但耗时 29ms（首页 2.3ms） |
| `getRecords(id,{limit:100})` 单活动 10 万点 | 解 **100000 点 / 15.4MB**，与全量等价（分页零收益） |
| `getRecordsByActivityIds` 500 活动×2000 点 | 解 **1000000 点 / 154MB** |
| 导出 `iterateRecordBatches` 10 万点/批 1 万 | 11 次调用解 **1100000 点 / 169MB**，**放大 11 倍** |

### 两个关键认知（与初稿方案不同）

1. **IDB 游标 `advance()` 不解对象**：`offset/limit` 跳页时解出行数 = limit，不随页深增长；
   代价只体现在遍历时间（29ms@offset950）。所以 keyset 分页**不必做**，千级活动下 offset 够用。
   → 这也意味着 P1-1 的收益比方案里预估的更彻底。
2. **分片（P1-2）的第一收益方是导出，不是详情页**。详情页无论如何都要读全量点画图，
   分片对它只是「降峰值」。真正的重灾区：
   - **`exportImport.ts:444` `iterateRecordBatches` 放大 11 倍**：按 offset 递增分批读，
     而 `getRecords` 每次都整行读出再 `slice` → N 次调用解 N 倍全量。分片后回落到 ≈1.0x。
     **这是整个重构收益最大、风险最低的一处。**
   - 批量扫描 154MB 峰值（6 处调用点：热力图/路线图/赛段页/赛段详情/赛段创建/赛段推荐）。
     注意：分片**不能**降低 `getRecordsByActivityIds` 的峰值（它返回 Map<string, 全量>），
     必须等 P1-3 把调用点改成流式迭代才有效。

### 片大小定案 2000 点（原方案写 5000，已下调）

导出场景两者持平（5000→跨 2–3 片 2.4MB；2000→跨 6 片 1.9MB），但详情页读 100 点上
2000 点明显更优（解 0.32MB vs 0.8MB），扫描峰值也是。典型活动 3600–10800 点 = 2–6 片。

### 分片迁移的取舍（已决定，写进方案 §8）

**不保留 `activity_blobs` 作回滚源**，按活动原子替换（写该活动 chunks + 删该活动 blobs 同事务）。
理由：纯前端应用存储配额是硬约束，翻倍不可接受；PWA `autoUpdate` 使客户端不会长期停在旧版本；
真需要回滚时应发布「能读 chunks」的补丁版本，而非退回更早 tag。
**代价**：降级到旧版本后轨迹不可见（数据在 chunks 里没丢，但旧代码无读取路径）——须在发布说明告知。

### 这轮最有价值的产出：**三项计划工作被实测否掉**

- **keyset 分页**：IDB 游标 `advance()` 不解对象，`offset/limit` 的解出行数恒等于 limit，
  尾页只是遍历慢（29ms）。千级活动下不值得做。
- **快照增量构建**：全量只要 7.0s，缓存 150MB+ 产物在 CI 上的上传下载比重建更慢。
- **产物 gzip 落盘 + 按年分片**：GitHub Pages 已对 JSON 做 gzip
  （`curl -H "Accept-Encoding: gzip"` 实测到 `Content-Encoding: gzip`，58944 → 15667 字节）。
  落盘 `.gz` 反而让 Pages 不再压缩；而 `records/<id>.json` 已是「详情页取一条活动」的最优粒度。

### 一个真实踩坑，值得单独记
